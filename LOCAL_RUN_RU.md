# Локальный запуск ABIevm и проверка StakeDAO

Проверенная версия Go: **1.27.2**. Откройте терминал в корне проекта — папке с `go.mod`.
При первом запуске Go скачает зависимости. Реальный RPC URL храните в переменной
окружения, не в исходниках. `.env` автоматически не читается.

## Если IDE не находит функции после обновления

`registryService.go` использует функции из других файлов того же Go-пакета:

- `readRegistryRanges` определена в `internal/service/stakedao/discovery.go`;
- `decodeVaultRegistration` определена в `internal/service/stakedao/StkDaoSRV.go`.

Это рабочие функции приложения, а не тестовые helpers. Все три файла должны
быть из одной версии ветки `feat/stakedao-service`, лежать в одной папке
`internal/service/stakedao` и начинаться с `package stakedao`.

При ручном обновлении безопаснее скачать весь архив ветки и распаковать в новую
папку. Сохраните свои локальные изменения отдельно и заново задайте переменные
окружения RPC и PostgreSQL в конфигурации запуска IDE. Не добавляйте предложенные
IDE заглушки функций. Вместе с сервисом нужны репозиторий, миграции, ABI,
`go.mod`/`go.sum` и подключение сервиса в приложении.

Из корня проекта, где находится `go.mod`, выполните в PowerShell:

```powershell
go build -mod=readonly ./...
```

Сборка не запускает сервер, не подключается к PostgreSQL и не тратит RPC/CU.
При первом запуске могут скачаться Go-зависимости. Если сборка успешна, а IDE
продолжает подсвечивать ссылки, проверьте открытый корень проекта и Go SDK,
перезагрузите Go Modules; затем при необходимости выполните в GoLand
`File → Invalidate Caches…` и перезапуск. Если сборка падает, ориентируйтесь
на её текст ошибки — это уже не только индексация IDE.

Карта файлов сервиса: [internal/service/stakedao/README.md](internal/service/stakedao/README.md#какие-файлы-за-что-отвечают).

## Проверка 1–5 реальных пулов с GetBlock

Команда запускается отдельно от сервера и Swagger. По умолчанию она берёт
до пяти gauge из вашего первоначального `gaugesMainFromController` (commit
`ec418eb`) и читает актуальную регистрацию через `Controller.gauge(address)`.
Адреса являются кандидатами, а не доказательством регистрации: источником vault,
asset, rewardReceiver и protocolId служит текущий контракт Controller.
История событий и исторический `eth_getCode` вообще не запрашиваются.
Все чтения состояния и расчёт наград выполняются на одном свежем блоке.

В PowerShell задайте URL своего **Ethereum Mainnet** endpoint:

```powershell
$env:STAKEDAO_ETHEREUM_RPC_URL = "ВАШ_GETBLOCK_MAINNET_RPC_URL"
```

Если в этой PowerShell уже есть правильный `$rpc`, вместо копирования URL:

```powershell
$env:STAKEDAO_ETHEREUM_RPC_URL = $rpc
```

Сначала проверьте один пул:

```powershell
go run -mod=readonly ./cmd/stakedao-check -limit 1 -output stakedao-sample.json
```

После успешного запуска появится `stakedao-sample.json` в текущей папке.
Команда напечатает полный путь. При ошибке новый файл не создаётся, предыдущий
успешный результат не перезаписывается. Это также относится к случаю, когда
команда завершилась с `exit status 1`: отсутствие JSON тогда ожидаемо.
Не используйте PowerShell pipe или перенаправление: за сохранение отвечает
`-output`, результат записывается в UTF-8 без BOM после успешного получения JSON.

Для проверки пяти пулов и сохранения JSON для разбора:

```powershell
go run -mod=readonly ./cmd/stakedao-check -limit 5 -output stakedao-sample-5.json
```

В Linux/macOS:

```sh
export STAKEDAO_ETHEREUM_RPC_URL="ВАШ_GETBLOCK_MAINNET_RPC_URL"
go run -mod=readonly ./cmd/stakedao-check -limit 1 -output stakedao-sample.json
go run -mod=readonly ./cmd/stakedao-check -limit 5 -output stakedao-sample-5.json
```

Команда делает не больше **5 RPC-запросов/с** и **300 RPC-попыток** за запуск.
Это ограничение запросов, не вычислительных единиц GetBlock: цена CU зависит от
метода. Лимит времени — 5 минут; прервать можно Ctrl+C. Автоматического перебора
других окон или повторной полной загрузки нет. Цены читаются из контрактов
Chainlink/ERC4626/Curve NG и кэшируются в памяти. Чтения цен тоже входят в RPC-бюджет.
Свежие цены компонентов повторно используются при проверке следующих пулов.
Между отдельными запусками команды локальная map не сохраняется; в веб-приложении
она живёт до остановки процесса. Redis пока не подключён.

В JSON смотрите `network`, `blockNumber`, `pools`, `errors`. В каждом пуле:
`name`, `vaultAddress`, `assetAmount`, `tvl`, `aprStatus`, `apr`, `rewards`.
`tvl` — USD, `apr` — годовая оценка наград в процентах. `apy` пока `null`.
Отсутствующая цена LP/asset не заменяется ценой компонента: TVL/APR могут быть
`null`, причина будет в `errors`. Диагностические сообщения идут в stderr,
без `-output` JSON идёт в stdout. Наличие JSON не означает, что все значения доступны или уже
подтверждены независимым сравнением с UI StakeDAO.

В выборке может оказаться меньше пулов, чем запрошено: незарегистрированные
и shutdown gauge пропускаются. Если все кандидаты неактивны, команда завершится
ошибкой с пояснением. Другие конкретные gauge можно передать явно:

```sh
go run -mod=readonly ./cmd/stakedao-check -limit 1 -gauges 0x3285987Bbd0b695Ac48DC8571F519065B50aBA07 -output stakedao-sample.json
```

Через `-gauges` допускается максимум пять уникальных ненулевых адреса через запятую.
Это адреса gauge, не LP-токены и не адреса vault. Curve V2 имеет поддержку основной
награды, Balancer primary — пока нет.

Предыдущая версия выбирала окно 23225415–23225514: пользователь подтвердил, что
в нём нет подходящих текущих регистраций. Успешный ответ `eth_getLogs` подтверждал
только доступность метода, а не наличие нужных vault. Это окно больше не используется
по умолчанию. Для ручной диагностики известного окна остаются совместные флаги
`-from`/`-to` (максимум 100 блоков включительно); с `-gauges` их совмещать нельзя.
Автоматического перебора окон нет.

Первый кандидат (`-limit 1`) — `evaUSDC/evaUSDT`, для которого в ручном
mainnet-запуске на блоке 26234474 получены TVL и APR. Пример результата трёх пулов
есть в `examples/stakedao-sample.json`; отдельный новый пример пяти —
`examples/stakedao-sample-5.json`. В нём avUSD/evaUSDC не имеет цены из-за
отсутствия USD feed для avUSD; для frxUSD/scrvUSD цена уже получена из контрактов; значения при новом запуске могут отличаться. Этот пример получен
через PublicNode, не через ваш GetBlock.

Если произошла ошибка, пришлите её текст без ключа и URL. Полный приватный endpoint
команда в диагностике скрывает. GetBlock Mainnet подтвердил `eth_getLogs` на
100 блоков, но отказал в историческом `eth_getCode`. Для новой проверки по gauge
оба метода не нужны. JSON может содержать `errors` и недоступные цены/компоненты
APR; наличие файла само по себе не подтверждает полноту или точность оценки.

Пять кандидатов: evaUSDC/evaUSDT, avUSD/evaUSDC, frxUSD/scrvUSD,
srRoyUSDC/frxUSD, frxUSD/evaUSDT. Первые три сохранены для сравнения с прежней
выборкой; два новых выбраны из вашего исходного списка после проверки текущей
регистрации и доступности контрактных цен. avUSD оставлен как случай отсутствующей
USD-цены: его TVL/APR могут быть `null`. Это не подстановка нулевой доходности.

**Проверка пяти пулов запускается командой выше, отдельно от Swagger.**
Swagger `GET /reservesStakedao/ethereum` по-прежнему выполняет полную загрузку.
Бюджет команды остаётся 300 попыток, не 300 CU. Сам факт успешного JSON не
доказывает точность APR: для независимой сверки нужны состав наград, комиссии,
тот же блок/время и сопоставимый reward APR, а не итоговый APY из UI.

Хранение регистраций в Postgres реализовано и включается через `DATABASE_URL`.
Ручная миграция через pgAdmin/psql и настройки IDE: [migrations/README.md](migrations/README.md).
Архитектура: `internal/service/stakedao/REGISTRY_STORAGE_PLAN_RU.md`.
Redis пока не требуется: цены остаются в map.

## Запуск веб-сервера

```sh
go run -mod=readonly ./cmd
```

Echo слушает порт 8081. Проверить только запуск без RPC можно запросом
`GET /reservesStakedao/base`: ожидается HTTP 400, поддерживается только `ethereum`.

Для полной загрузки выберите в Swagger `GET /reservesStakedao/ethereum`.
Теперь он читает события по 1500 блоков, используя до 8 воркеров, и не требует
архивного `eth_getCode`. Для Ethereum сохранён блок начала 23225415 из прежнего
поиска через Alchemy; источник номера описан в README StakeDAO.

Параметры до запуска сервера (например, PowerShell):

```powershell
$env:STAKEDAO_ETHEREUM_RPC_URL = "ВАШ_GETBLOCK_MAINNET_RPC_URL"
$env:RPC_MAX_RPS = "18"
$env:STAKEDAO_DISCOVERY_WORKERS = "8"
go run -mod=readonly ./cmd
```

RPC_MAX_RPS ограничивает суммарные HTTP RPC-методы Aave/Curve/StakeDAO в этом
процессе, а не каждую платформу отдельно. При запуске из IDE задайте переменные
в её Run Configuration: переменные другой PowerShell сессии туда не передаются.
Работает только HTTP(S), не WebSocket. Для нескольких экземпляров сервера/CLI
лимит каждого процесса считается отдельно.

Полный запрос ограничен пятью минутами. ~2000 запросов событий при 18 RPS —
теоретически ~112 секунд, затем нужны чтения пулов и цен. Время и расход CU
полной mainnet-загрузки ещё не измерены; при нехватке CU или времени будет ошибка,
а не неполный список под видом полной загрузки. С настроенным Postgres прогресс
регистраций сохраняется после каждого диапазона: следующий запуск продолжит с
последнего обработанного блока. Первичная загрузка дополнительно читает headers
для проверки hash; оценка ~112 секунд учитывает только запросы logs, не эти чтения.
Без `DATABASE_URL` остаётся прежний режим полного сканирования.
Контрактные чтения StakeDAO теперь используют Multicall3 группами до 24
под-вызовов на одном snapshot-блоке. Метаданные пула (5 getter) читаются одним
`eth_call`; параметры наград — несколькими зависимыми этапами. Multicall включён
автоматически и для Swagger, и для `stakedao-check`; дополнительные переменные
для его включения не нужны. Загрузка цен через отдельный сервис остаётся
самостоятельными чтениями. CU группы может стоить больше одиночного getter.
Изменения этой оптимизации относятся только к StakeDAO.

Ограниченная команда для 1–5 пулов остаётся удобной для дешёвой диагностики.

## Сохранение регистраций в Postgres

Один раз примените `migrations/000001_registry.up.sql` в своей базе, затем задайте
`DATABASE_URL` в терминале/Run Configuration до запуска сервера. Полные команды
для вашего установленного Postgres (pgAdmin/psql) и необязательного Docker — в
[migrations/README.md](migrations/README.md). Миграции не выполняются автоматически.

Echo получает пул из `cmd/main.go`; сервис синхронизации находится в
`internal/service/stakedao/registryService.go`, SQL — в
`internal/repository/stakedao/registryPostgres.go`. При заданном, но неработающем
подключении сервер не делает fallback на полную загрузку.

В логах при работе с БД смотрите `registry_saved_block`, `registry_target_block`
и этапы `registry_lock`, `registry_checkpoints`, `registry_finalized`, `registry_tail`.
В Postgres сохраняется finalized-история и не больше 16 контрольных точек.
Реорганизация откатывает события и курсор вместе. Проверка 1–5 пулов из CLI
по-прежнему работает напрямую по Controller, без БД.

В БД сохраняются регистрации, а не рассчитанные данные пулов. `pools_loaded`
относится только к текущему запросу: после его ошибки расчёт пулов начинается
заново на новом snapshot. Загрузка всей истории регистраций не гарантирует, что
чтение всех пулов и цен уложится в дневной бюджет CU или таймаут.

Полная загрузка теперь обрабатывает до 8 пулов одновременно и объединяет их
getters в общую очередь Multicall. Одинаковые чтения общих контрактов выполняются
один раз на snapshot; кэш не сохраняется между запросами. Для этой оптимизации
обновите весь код ветки `feat/stakedao-service` и перезапустите сервер; новых
SQL-миграций для уже настроенного реестра не требуется. После обновления в логах
этапа `pools` должно быть `pool_workers=8` для списка из 359 кандидатов.

## Если Swagger вернул 504

Общий лимит полной загрузки — **5 минут**, отдельного HTTP-запроса к RPC —
**45 секунд**. Оба таймаута приводят к 504, поэтому одного ответа Swagger
недостаточно для определения этапа сбоя.

В консоль IDE / stderr теперь пишутся `StakeDAO load`: при смене этапа,
каждые 15 секунд во время загрузки и при завершении. По `request` можно
отделить параллельные загрузки. Важные поля:

- `stage=discovery`, `registry_finalized`, `registry_tail`: события;
  `ranges_done/ranges_total` — завершённые диапазоны текущего сканирования.
  При переходе от finalized-истории к незавершённому участку счётчик начинается
  заново. `last_range_from/to` — последний успешно обработанный диапазон;
- `stage=pools`: данные пулов; `pools_visited/pools_total` — число обработанных
  кандидатов, `pools_loaded` — число добавленных пулов. Завершение работ может идти
  в другом порядке, чем адреса в discovery; итоговый JSON сохраняет прежний порядок.
  `pool_workers` — число обработчиков пулов (до 8); поле `workers` относится к
  последнему чтению диапазонов событий. `gauge` — последний обработанный кандидат;
- `stage=prices`: чтение/кэширование цен; `stage=verify_snapshot` — финальная проверка;
- `rpc_logs`, `rpc_calls`, `rpc_errors`, `rpc_active` — вызовы событий,
  контрактов, ошибки и текущие попытки, включая ожидание локального лимитера;
- `event=request_deadline failure=request_timeout`: истёк общий deadline
  (5 минут либо более ранний deadline вызывающей стороны);
- `event=failed failure=rpc_timeout`: завершился с таймаутом отдельный RPC-вызов,
  при этом общий deadline ещё не истёк;
- `first_rpc_failure_method/stage`, `first_rpc_http_status`, `first_rpc_error_code`:
  первая ошибка RPC сохраняется, даже если позднее запрос упёрся в общий deadline.
  При наличии HTTP/RPC ошибки в окончательной причине также выводятся
  `rpc_http_status` / `rpc_error_code`.

Счётчики — попытки RPC-методов, **не CU** и не гарантированное число запросов,
принятых провайдером. Одна группа Multicall считается одним `eth_call`.
Полные URL, calldata и тексты ошибок провайдера в этих логах не печатаются.

`event=failed rpc_http_status=402` означает, что провайдер вернул HTTP Payment
Required. Проверьте баланс CU и состояние подписки в его кабинете. Если CU
исчерпаны, увеличение RPS, числа воркеров или таймаута не восстановит доступ.

Если GetBlock показывает **CU balance = 0**, не повторяйте полную загрузку до
восстановления/пополнения квоты. 20 RPS ограничивает скорость, 50K CU/day —
объём вычислений; снижение RPS или увеличение времени ожидания не добавляет CU.
Multicall тоже расходует CU и не сокращает историю `eth_getLogs`.
С Postgres сохранённая finalized-история не перечитывается: синхронизация
продолжается с курсора, свежий незавершённый участок дочитывается отдельно.
Без `DATABASE_URL` полный endpoint по-прежнему сканирует историю заново.
При нулевых CU уже сохранённые диапазоны не пропадают; продолжать загрузку имеет
смысл после восстановления квоты. Настройка БД — `migrations/README.md`.

После восстановления CU для дешёвой проверки используйте сначала
`stakedao-check -limit 1`, как показано выше. Если повторяется 504 при полной
загрузке, сохраните последние строки `StakeDAO load`, особенно итоговую с
`event=request_deadline`/`event=failed`: они покажут этап и объём выполненной работы.
Повторять массовое сканирование ради сбора логов при нулевом балансе не нужно.

## Автоматические проверки

```sh
go test -mod=readonly -p 3 ./...
```

Тесты используют локальные HTTP/RPC-стенды, не бесплатные RPC.
Бизнес-модель и источники ABI: `internal/service/stakedao/README.md`.
Изменения публикуются в ветке `feat/stakedao-service`, без изменения `main`.
