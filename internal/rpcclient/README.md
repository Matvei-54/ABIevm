# Общий лимит HTTP JSON-RPC

Все рабочие точки создания RPC-клиента в Aave, Curve и StakeDAO используют
`rpcclient.DialContext`. Сгенерированные ABI-bindings получают этот же клиент,
поэтому ограничиваются реальные RPC-методы (`eth_call`, `eth_getLogs`, headers,
chain ID и т. д.), а не только запуск обработки одного пула.

Один limiter разделяется всеми HTTP(S) endpoints внутри процесса приложения.
Это консервативный суммарный лимит даже при разных провайдерах. По умолчанию —
**18 RPC-методов/с** с интервалом между отправками, без стартового burst.
`RPC_MAX_RPS` задаёт целое 1–10000 и читается при создании первого клиента.
Чтобы изменить его в работающем сервере, перезапустите процесс с новой настройкой.

JSON-RPC batch учитывается по числу методов; batch больше секундной квоты
отклоняется локально, его нужно разделить. Один Multicall `eth_call` считается
одним RPC-методом, но его CU/gas стоимость зависит от провайдера и содержимого.
HTTP timeout — 45 секунд, ожидание лимитера отменяется через request context.
Автоматических повторов 429 или бесконечных retries нет.

Лимит действует только внутри одного процесса: другой сервер, IDE, PowerShell
или отдельная CLI-команда имеют собственную квоту. При одновременном использовании
одной учётной записи GetBlock их суммарную нагрузку нужно учитывать отдельно.
Это не распределённый limiter; Redis в него не добавлен. HTTP-запросы к обычным
API цен/обозревателям не расходуют RPC RPS и не проходят через этот transport.
WebSocket/IPC этим клиентом не поддерживаются.

Существующие worker/ticker-механизмы Curve сохранены. `recursivePools` и расчёты
других платформ не менялись. Клиенты разных платформ используют общий transport
limiter без объединения их бизнес-логики.

Тесты: конкурирующие запросы двух RPC-клиентов к локальному серверу, отмена
ожидания, сохранение JSON-RPC body и учёт стоимости batch по методам. Внешние
RPC в автоматических тестах не используются.
