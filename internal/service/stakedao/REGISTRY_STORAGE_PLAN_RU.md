# План хранения регистраций пулов

Это предложение для согласования. В текущей реализации БД, Redis и инкрементальная
синхронизация регистраций ещё не подключены. Curve и Aave эта правка не меняет.

Предлагаю **Postgres для постоянного реестра**, Redis — позднее как кэш цен,
готовых расчётов и, если понадобятся несколько экземпляров приложения, блокировок.
На первом этапе хватит одного Postgres и существующей map цен. Отдельный Redis
ради сохранения нескольких тысяч регистраций сейчас не обязателен.

## Какие данные хранить

| Сущность | Ключ | Содержимое |
| --- | --- | --- |
| Регистрация пула | chain ID + платформа + Controller/Factory + gauge/pool | vault, asset, rewardReceiver, protocolId, статус, координаты последнего изменения |
| Курсор синхронизации | chain ID + платформа + Controller/Factory + версия обработчика | последний **полностью обработанный** блок, его hash, начальный блок |
| Метаданные токена | chain ID + адрес | symbol, decimals, проверенные связи с underlying/oracle, время/блок проверки |
| Журнал недавних изменений | ключ реестра + block/tx/log | предыдущая версия записи для отката при реорганизации; хранится ограниченное окно |

Адреса EVM удобно хранить как 20 байт, hash — 32 байта. Текстовые поля нужны для
названий и символов, а не для дублирования всего RPC JSON. Один токен используется
несколькими платформами через один ключ `(chainID, address)`: копировать его
метаданные отдельно для каждой платформы не требуется. Символ токена ключом быть
не может. В других EVM-сетях тот же адрес — отдельная запись с другим chain ID.

Текущие цены и TVL/APR не являются регистрациями. Их обновляем отдельно, с
ограниченным сроком годности: map сейчас, Redis при необходимости. Не записываем
новую историческую строку цены или APR при каждом запросе пользователя.

## Как обновлять

1. При первой синхронизации читаем события от известного блока создания Controller
   диапазонами по 1500, с текущим общим ограничением RPS. Первичная загрузка всё ещё
   расходует CU: БД не устраняет эту стоимость.
2. Сохраняем результат каждого последовательного завершённого диапазона и его
   курсор **одной транзакцией**. Даже пустой диапазон продвигает курсор. Завершённый
   более поздний диапазон от параллельного воркера не позволяет перескочить через
   ещё не прочитанный диапазон. При ошибке/исчерпании CU возобновляем с сохранённого
   курсора, без повторения всей истории.
3. В следующий раз читаем от `last_scanned_block + 1` до выбранного безопасного
   верхнего блока. Это именно последний просканированный блок, не блок последнего
   найденного события: иначе пустые участки придётся сканировать снова.
4. Новую регистрацию добавляем, изменённую обновляем через upsert. Для StakeDAO
   учитываем также `GaugeShutdown`/`GaugeUnshutdown`, которые присутствуют в ABI
   Controller. Текущий статус и принадлежность vault/asset дополнительно проверяем
   через Controller перед расчётами. Изменения Accountant/fees читаем из контрактов,
   не считаем навечно неизменными из-за наличия регистрации в БД.
5. При расчёте используем найденные адреса, затем читаем свежие активы и награды
   через Multicall и цены через существующий price service. Реестр не заменяет
   эти чтения и не делает устаревший APR актуальным.

Для нескольких процессов нужен один синхронизатор на ключ реестра — например,
транзакционная advisory lock в Postgres. Redis для этой блокировки не обязателен.

## Реорганизации и согласованность

Для каждой сети отдельно определяем безопасный верхний блок: `finalized`, где
это корректно поддерживается, либо согласованная глубина подтверждений. Число
подтверждений нельзя автоматически переносить с Ethereum на все L2.
Новые пулы появятся в сохранённом реестре после этой задержки; если понадобится
показывать самые свежие блоки, для них нужен отдельно обрабатываемый временный хвост.

Перед продолжением сверяем сохранённый hash блока с сетью. При несовпадении
находим последнюю совпадающую контрольную точку и откатываем **и записи, и курсор**
по журналу недавних изменений, затем перечитываем события. Просто уменьшить
номер курсора недостаточно: записи из отменённых блоков могут остаться в таблице.
Если реорганизация глубже сохранённого окна, требуется восстановление из
проверенной контрольной точки/пересборка; повреждённый реестр не выдаём за актуальный.
Журнал чистим согласно политике финальности сети, не накапливаем всю историю.

## Подойдёт ли другим платформам

Да, общий механизм — постоянный реестр, курсор, атомарное обновление, проверка
сети и откат — можно переиспользовать. Способ обнаружения остаётся отдельным
адаптером платформы: StakeDAO использует Controller и события регистраций,
Curve — свои factories/registries, Aave может перечислять reserves через getter.
Если платформа даёт полный недорогой список одним методом, сканировать события
ради единого подхода не нужно. Наличие БД не добавит автоматически поддержку
новых блокчейнов или новых формул оценки LP.

## Оценка размера

Для планирования можно заложить **1–3 КБ на регистрацию с индексами**, без ценовой
истории, WAL, резервных копий и больших JSON. Это оценка, не измерение нашей схемы:

| Всего регистраций во всех сетях/платформах | Ориентир для таблицы и индексов |
| --- | --- |
| 1 000 | 1–3 МБ |
| 10 000 | 10–30 МБ |
| 100 000 | 100–300 МБ |
| 1 000 000 | 1–3 ГБ |

Метаданные токенов и ограниченный журнал увеличат размер. Общий диск Postgres
также включает служебные данные, WAL и резервные копии; они не входят в таблицу.
После первичной загрузки нужно измерить `pg_total_relation_size`, настроить
autovacuum и удержание WAL/бэкапов. Upsert сам по себе не отменяет обслуживания БД.

Главный источник быстрого роста — хранение временных рядов без ограничений.
Например, 10 000 пулов × 1 запись в минуту = **14,4 млн строк в сутки**.
Такую историю сейчас не предлагаю: для реестра достаточно актуальных записей
и небольшого окна изменений. Общий размер определяется количеством объектов,
а не количеством уже существующих блоков во всех сетях.
