# StakeDAO: текущее состояние интеграции

## Какие файлы за что отвечают

| Файл | Назначение |
| --- | --- |
| `StkDaoSRV.go` | Загрузка пулов, TVL и награды; декодер `decodeVaultRegistration`. |
| `stakeDaoService.go`, `abi/` | ABI контрактов и адрес Controller; JSON ABI встраиваются в бинарник. |
| `discovery.go` | Чтение событий диапазонами и воркерами; `readRegistryRanges`. |
| `registryService.go` | Синхронизация регистраций, проверка курсора и реорганизаций. |
| `registryStore.go` | Интерфейс хранилища и типы событий/курсора. |
| `multicall.go` | Объединение чтений контрактов в Multicall3. |
| `progress.go` | Логи этапов и прогресса загрузки. |
| `sample.go` | Ограниченная проверка 1–5 явно выбранных пулов. |
| `dto/stakeDaoDTO.go` | Структура ответа API. |
| `../../repository/stakedao/registryPostgres.go` | Реализация хранилища в PostgreSQL. |

Файлы `registryService.go`, `discovery.go` и `StkDaoSRV.go` используют общие
приватные функции: они должны быть одной версии, находиться в одной папке
`internal/service/stakedao` и иметь `package stakedao`. Объявлять заглушки для
`readRegistryRanges` или `decodeVaultRegistration` не нужно. Если IDE не находит
эти функции после копирования файлов, обновите весь проект из одной версии ветки
`feat/stakedao-service`, включая `go.mod`, `go.sum`, зависимости и ABI.
Порядок действий: [локальный запуск](../../../LOCAL_RUN_RU.md#если-ide-не-находит-функции-после-обновления).

`GET /reservesStakedao/ethereum` читает регистрации, метаданные и количество
активов на одном блоке. По умолчанию HTTP-ответ сокращён до
`name/apr/symbol/address/apy/status` для каждого пула. `address` — vault,
`status` — прежний `aprStatus`, не статус активности. Все детали, включая TVL,
награды и ошибки, возвращаются с `?details=true`. Обёртка краткого ответа
сохраняет сеть и номер блока. Сервис/ручная команда по-прежнему возвращают полные DTO.

`GET /reservesStakedao/ethereum/diagnostics` читает только crvUSD/USDC и FXS/ETH
через `GetRewardDiagnostics` и ограниченный sample-путь: без logs/БД,
5 RPC/с, 300 попыток. Текущие vault/asset проверяются через Controller.
Эти два пула не исключаются из общего списка. Описание запуска/скачивания:
[LOCAL_RUN_RU.md](../../../LOCAL_RUN_RU.md#скачать-обновление-и-открыть-swagger).

Общий `prices.TokenPriceService` сначала проверяет
`MemoryStore`, затем получает отсутствующие цены через `ContractSource` на том же
блоке: Chainlink USD feeds, ERC4626 conversion, оценка plain Curve StableSwap NG
и неметапулов MetaRegistry через состав/балансы и totalSupply.
DeFiLlama в StakeDAO больше не используется.
`GetTokenPrice` читает только кэш, ключ — `(chainID, address)`, TTL — 15 минут с
дополнительным ограничением срока годности оракула/компонентов (`ValidUntil`).
Для будущего Redis достаточно реализовать `prices.Store`.
Подробности и ABI-источники: `internal/service/prices/README.md`.

`assetAmount` — точная десятичная строка с количеством LP/asset-токенов.
`tvl` — количество активов × USD-цена именно этого asset/LP-токена. Цену LP
не подменяем ценой одного из его компонентов. При достоверном нулевом количестве
`tvl: 0` определяется без USD-котировки; `apr: null` остаётся из-за нулевого TVL.
Если количества нет или для положительного количества нет свежей цены,
`tvl: null`, причина находится в `errors`.

Для цен выбираются только активы vault с известным положительным количеством и
награды с известной положительной скоростью. Пустые vault, завершённые потоки и
неизвестные rates не вызывают лишних запросов цены. Это не подменяет неизвестную
цену/доходность нулём и не фильтрует сами пулы из ответа.

## Награды и APR

`rewardMechanism: accountant` обозначает учёт наград через контракт Accountant
StakeDAO V2. Наличие этого механизма не означает, что прочитаны все скорости
наград. Полноту отдельно показывает `aprStatus` (в кратком ответе `status`).

`curvePrimaryRate` фиксирует место проверки и возвращает структурированную
ошибку: `code`, `stage`, `contract`, `method`, безопасное `message`.
Различаются стратегия/Accountant/токены, физическое размещение и его сверка,
targets, комиссии/политика harvest, getters Curve gauge и Convex Sidecar.
Входящие RPC-тексты не копируются в JSON. Ошибки проверки не превращаются в
нулевой primary rate; остальные известные rewards могут дать только `partial`.
Конкретный getter или проверка видны в `errors` полного ответа и diagnostic route.

`aprScope: rewards` означает оценку наград, без торговых комиссий/роста стоимости
LP и без реинвестирования. `apy` остаётся `null`. APR — экстраполяция текущих
скоростей на 365 дней, а не обещание получения наград в течение года.

Для Ethereum Curve V2 читаются актуальные Accountant, основной токен, Strategy,
Locker и allocation targets. Сверяются Accountant/токены/принадлежность Sidecar
и соответствие физических активов Strategy количеству активов vault.

Основная скорость CRV:

- Locker: `inflation_rate × gauge_relative_weight × working_balance / working_supply`.
- Convex: `rewardRate × sidecar.balanceOf / baseRewardPool.totalSupply`;
  завершённый `periodFinish` даёт нулевую скорость.
- Accountant: protocol fee вычитается только из Locker-части.
  При CHECKPOINT harvest fee вычитается из обеих частей; при HARVEST его нет.
  Проценты читаются из контракта и масштабируются на `1e18`.

Дополнительные награды читаются из **RewardVault**, а не из внешнего Curve gauge:
`getRewardTokens()`, `rewardData(token)`. Их скорость равна
`rewardRate / 10^(18 + tokenDecimals)`. Учитываются время блока и срок наград.
Эти потоки уже распределяются самим vault и не получают повторное удержание
комиссий Accountant. Подтверждённая законченная награда имеет скорость ноль;
ошибка чтения или отсутствие цены не заменяются нулём.

`rewards` содержит компоненты, скорости, сроки и отдельные APR.
`aprStatus: available` означает, что доступен поддерживаемый основной механизм,
полный список extra-потоков и все необходимые цены. `partial` означает сумму
только доступных компонентов; `unavailable` — отсутствие пригодного расчёта.
Для Balancer/неизвестных Sidecar основной механизм пока не реализован:
возможен только partial APR дополнительных наград. Не предполагается совпадение
с итоговой доходностью UI StakeDAO, включающей другие источники yield.

ABI встроены в бинарник через `go:embed` (каталог `abi`); приложение не обращается
к Etherscan или StakeDAO API. Источники и точные адреса — в `abi/README.md`.
Поддержка схемы проверена локальным RPC-стендом и ограниченным mainnet-запуском.
Для полного Ethereum endpoint загрузка событий теперь идёт по 1500 блоков с
ограниченным числом воркеров, без архивного `eth_getCode`.

## Полная загрузка через Swagger

`GET /reservesStakedao/ethereum` использует начало **23225415** для текущего
Controller `0x2d8BcE1FaE00a959354aCD9eBf9174337A64d4fb`, фиксирует верхний блок и
распределяет диапазоны `eth_getLogs` по **1500 блоков включительно**.
По умолчанию работают 8 воркеров; `STAKEDAO_DISCOVERY_WORKERS` допускает 1–64.
Очередь потоковая и ограниченная, без создания горутины на каждый диапазон.
Результаты сортируются по block/transaction/log index до выбора последней
регистрации: порядок завершения HTTP-запросов не влияет на итог.
Ошибка любого диапазона отменяет остальных; частичный discovery не выдаётся
за полный список. Проверяются собственные границы каждого ответа и финальный
snapshot hash. С `DATABASE_URL` используется постоянный реестр Postgres:
finalized-диапазоны сохраняются по порядку, следующий запрос читает только новые.
При пустом `DATABASE_URL` остаётся прежний режим полного сканирования.

Источник номера начала: прежний live-запуск пользователя через Alchemy успешно
прошёл бинарный поиск первого блока с кодом, после чего `eth_getLogs` упал на
диапазоне **23225415–23227414**. Сохраняется результат именно того поиска.
В текущей среде архивный `eth_getCode` снова недоступен; независимо получить
receipt создания не удалось. Нового подтверждения через receipt здесь не
заявляется. При смене Controller номер нужно проверить заново.

`STAKEDAO_CONTROLLER_DEPLOYMENT_BLOCK` позволяет явно переопределить номер
положительным десятичным значением. Не повышайте его произвольно ради скорости:
так можно пропустить ранние регистрации. Историческое состояние для поиска
начала больше не запрашивается; актуальные контрактные данные читаются на
фиксированном свежем блоке, как и раньше.

Общий HTTP RPC-лимит Aave/Curve/StakeDAO — 18 RPC-методов/с по умолчанию,
настраивается через `RPC_MAX_RPS` до запуска процесса. Подробнее в
`internal/rpcclient/README.md`. Настройка workers задаёт параллелизм, а не
отдельную квоту RPS для каждого воркера или платформы.

Таймаут полного запроса остаётся 5 минут. Около 3 млн блоков требуют ~2000
запросов событий: нижняя оценка при 18 RPS — ~112 секунд только для logs.
Дополнительно нужны задержки RPC, данные пулов, цены и квота CU. Полная загрузка
за 5 минут пока не подтверждена реальным end-to-end запуском. GetBlock пользователя
подтвердил диапазоны до 1501 включительно; PublicNode из облака по-прежнему
отклоняет исторический `eth_getLogs` (403), поэтому массовый mainnet scan здесь
не выполнялся. Локальные тесты проверяют полный endpoint с несколькими диапазонами.

### Диагностика долгой загрузки

`GetPools` пишет структурированные логи через `log/slog` в стандартный logger
(по умолчанию stderr, виден в консоли IDE). Логи имеют идентификатор `request`,
этап, elapsed, прогресс диапазонов/пулов, счётчики попыток RPC; heartbeat — каждые
15 секунд. По завершении выводится `completed`, `failed` или `request_deadline`.
Последнее означает, что истёк общий контекст загрузки; `failed` с
`failure=rpc_timeout` — таймаут отдельного RPC при ещё действующем контексте.
Первая ошибка RPC сохраняется отдельно с методом, этапом и доступным HTTP-статусом /
числовым JSON-RPC кодом. Это помогает увидеть ошибку квоты до последующего таймаута.
URL, исходные тексты ошибок и тела ответов не логируются.

Сбор статистики потокобезопасен для discovery workers; heartbeat останавливается
и дожидается завершения при выходе из запроса. Таймауты 5 минут / 45 секунд,
диапазон событий 1500 и RPS не изменены. Проверки используют локальные fixtures,
включая общий deadline, отдельный RPC timeout и HTTP 429 без раскрытия ключей.
При CU balance = 0 повтор полной загрузки не восстановит данные; необходимы
восстановление квоты либо согласованная оптимизация повторного сканирования.
Подробнее о чтении логов — `LOCAL_RUN_RU.md`, раздел «Если Swagger вернул 504».

### Multicall в StakeDAO

Multicall3 подключён к полному endpoint и команде проверки 1–5 пулов. Адрес
Ethereum Mainnet: `0xcA11bde05977b3631167028862bE2a173976CA11`.
ABI `aggregate3` в `multicall.go` — подмножество уже имеющегося
`contracts/curve/Multicall3Curve.json`; совместимость кодирования проверяется тестом.
Реализации Curve и Aave в этой правке не менялись.

Чтения объединяются по этапам:

- текущие регистрации через `Controller.gauge`;
- имя, символы, decimals и totalAssets пула — 5 getter в одном `eth_call`;
- проверка Accountant, параметры Strategy/fees, Curve gauge и Convex Sidecar;
- extra rewardData и decimals токенов из проверенного списка наград.

В одной группе максимум **24 под-вызова**. Адреса для зависимых этапов сначала
получаются из предыдущих чтений. Внутри `aggregate3` под-вызовы выполняются
последовательно; это один запрос к RPC, без отправки транзакции и оплаты газа
кошельком. Все группы используют тот же фиксированный номер блока, что и остальные
чтения. В конце по-прежнему проверяется hash блока на реорганизацию.

Для каждого getter задан `allowFailure=true`: revert или некорректный ABI-ответ
помечает только соответствующее поле как недоступное; неизвестные данные не
заменяются нулём. Критическая ошибка чтения Controller прерывает запрос.
Транспортная ошибка/некорректный ответ всей группы передаётся всем её результатам;
автоматического повтора отдельными RPC-вызовами нет. `msg.sender` внутри
под-вызовов — Multicall3, поэтому объединены только явно выбранные getter,
не зависящие от вызывающего адреса. Зависимые адреса сначала читаются из предыдущих
результатов; getters с этими адресами затем тоже попадают в очередь Multicall.
Загрузка цен через отдельный price service использует прежний путь чтения.

Полный endpoint обрабатывает до **8 пулов одновременно**. Их getters собирает
одна общая очередь: адреса разных пулов могут оказаться в одном `aggregate3`,
сохраняется ограничение 24 под-вызова на батч. Диспетчер выполняет один внешний
`eth_call` за раз через общий RPS-лимитер. Очередь ограничена 192 элементами,
зависимые чтения продолжаются после получения нужных адресов.

Идентичные `(target, calldata)` объединяются, включая одновременные чтения
Accountant/Strategy/decimals. Кэш относится только к этому запросу и его блоку;
между блоками/пользователями он не переиспользуется. Каждый потребитель отдельно
декодирует ABI-ответ, чтобы не разделять изменяемые `big.Int` и срезы.
Порядок пулов и диагностик в JSON соответствует порядку discovery. Транспортная
ошибка, включая HTTP 402, останавливает очередь и работников без повторов;
отмена запроса дожидается их завершения. Ошибка отдельного getter остаётся
диагностикой поля. Ручная команда 1–5 пулов сохраняет последовательный отбор,
лимиты 5 RPS/300 попыток и использует кэш внутри выбранного snapshot.

На локальных подготовленных данных пять пулов дали одинаковые значения и порядок
при **50 → 10 `eth_call`**. Текущий полный сценарий на 359 пулов использует холодный
кэш и реальный `ContractSource` с подготовленными контрактными ответами: 359 разных
asset и общий reward token получают USD-цены через 1080 прямых вызовов оракулов.
Количество Multicall-батчей зависит от планирования обработчиков. Это тестовые
контракты; результаты не являются оценкой полного mainnet или стоимости GetBlock.

Этап `prices` использует до **8 обработчиков токенов**, оставаясь под общим RPS
лимитом. Одинаковые контрактные чтения и неуспешные пробы общих компонентов
объединяются в пределах одного `FetchAt` и его snapshot. На примере 20 LP с общим
компонентом без USD-источника число вызовов уменьшилось с 285 до 209 при прежних
результатах. Оракулы по-прежнему вызываются напрямую для сохранения поведения
проверок доступа. Подробнее: [сервис цен](../prices/README.md).
В логах появились `price_workers`, `rpc_reverts`, `first_rpc_failure=contract_revert`.
Сетевая/HTTP-ошибка цен завершает запрос ошибкой RPC, отсутствие цены отдельного
токена оставляет TVL/APR недоступными. Полная загрузка mainnet после оптимизации
этого этапа здесь не выполнялась; расход пользовательских CU тесты не используют.

Ручная проверка одного реального evaUSDC/evaUSDT через PublicNode на блоке
26241935 прошла без диагностических ошибок: TVL 3 820 330.40 USD,
reward APR 12.6955%. Это snapshot, не сверка с UI StakeDAO.

Общий RPS-лимитер и бюджет CLI считают внешние JSON-RPC-методы: одна группа
Multicall — один `eth_call`. CU и вычислительная стоимость зависят от провайдера;
уменьшение числа запросов не означает пропорционального уменьшения CU.
Multicall не объединяет `eth_getLogs` и не снимает предел диапазона 1500 блоков.

### Два RPC-провайдера

Сейчас используется один `STAKEDAO_ETHEREUM_RPC_URL`. Подключение второго
провайдера в этой правке не добавлено. Для GetBlock + Alchemy можно отдельно
маршрутизировать logs в GetBlock (проверенные 1500 блоков), а часть текущих
контрактных чтений/Multicall — в Alchemy. Общий текущий лимит `RPC_MAX_RPS`
сам по себе не даст суммировать их пропускную способность: потребуются
лимитеры по провайдеру/аккаунту, учёт CU и проверка chain ID/одинакового hash
фиксированного блока на обоих RPC. Ограничение Alchemy Free в 10 блоков
для logs остаётся; слепое чередование всех запросов между URL не подходит.
Два URL одного аккаунта могут делить общую квоту. Тарифные CU/s и лимиты
Multicall необходимо проверять отдельно от RPS.

## Ограниченная ручная проверка с GetBlock

```sh
# Перед запуском задайте STAKEDAO_ETHEREUM_RPC_URL своего Ethereum Mainnet endpoint.
go run -mod=readonly ./cmd/stakedao-check -limit 1 -output stakedao-sample.json
go run -mod=readonly ./cmd/stakedao-check -limit 5 -output stakedao-sample-5.json
```

По умолчанию `GetPoolsForGauges` читает текущий `Controller.gauge(address)` для
явных кандидатов из первоначального списка пользователя `gaugesMainFromController`
в commit `ec418eb`:

- `0xbE6228125448E40F5DCBB2DbdF7fF3F5721000B4`
- `0x3285987Bbd0b695Ac48DC8571F519065B50aBA07`
- `0x326b6d1a26Fd04afAa349340022076b5a2eb0c7C`
- `0xa5F5DBdFc6baFc69bb4107AF97Ca79519304Dbd7`
- `0x8F4e42343AF1CBF4f364cE448252d801E3f73937`

Кандидаты заданы только в ручной команде, не в production discovery. Их актуальные
vault, asset, rewardReceiver, protocolId и shutdown читаются из Controller на
свежем snapshot-блоке; неподтверждённые регистрации не используются. Затем
работают общие функции метаданных, TVL, наград и финальная проверка hash блока.
Нет `eth_getLogs` и `eth_getCode`. Свои gauge можно передать через `-gauges`:
1–5 уникальных ненулевых адресов через запятую. `-limit 1` проверяет только первого
кандидата; `-limit 5` — до пяти. Неактивные кандидаты могут уменьшить выборку.

Предыдущий default — окно 23225415–23225514 — не дал подходящих регистраций
при запуске пользователем. Оно больше не используется по умолчанию. Ручной режим
`GetPoolsSample` с `-from`/`-to` сохранён для явно выбранных окон до 100 блоков;
его нельзя совмещать с `-gauges`. Полного перебора окон нет.

Ограничения — 5 RPC-запросов/с, 300 попыток и 5 минут. При исчерпании бюджета
команда завершается ошибкой. CU зависит от метода. Контрактные чтения цен
также учитываются в этом RPC-бюджете. `-output` записывает UTF-8 JSON только после успешной загрузки: при
ошибке предыдущий файл сохраняется, новый не создаётся. Без флага JSON идёт в
stdout; сводка — в stderr, приватные URL скрываются в фатальных ошибках.

Подробные команды PowerShell в `LOCAL_RUN_RU.md`. Полный Swagger endpoint
теперь использует диапазоны по 1500 и сохранённый блок начала; см. раздел выше.
Наличие JSON может сопровождаться
`errors`, `null` в ценах/доходности и частичной оценкой наград.

## Хранение регистраций в Postgres

Реализованы [registryService.go](registryService.go), интерфейс
[registryStore.go](registryStore.go), Postgres-репозиторий и миграция.
Подключение/запуск: [../../../migrations/README.md](../../../migrations/README.md).
Архитектура: [REGISTRY_STORAGE_PLAN_RU.md](REGISTRY_STORAGE_PLAN_RU.md).

События и курсор записываются одной транзакцией для каждого диапазона до 1500
блоков, включая пустые диапазоны. Параллельные результаты фиксируются по порядку;
при сбое обработанные диапазоны сохраняются. Advisory lock сериализует writers
одного chain/platform/Controller между процессами. Хранятся finalized-события и
16 последних контрольных точек; незавершённый участок до snapshot читается заново.
При reorg откатываются история и курсор, при слишком глубоком reorg — безопасная
ошибка без автоматического сброса БД. Нет fallback при ошибке настроенного хранилища.

Перед расчётами `Controller.gauge` заново проверяет vault/asset, receiver, protocolId
и shutdown на блоке snapshot. Цены, TVL/APR и Redis в БД этой правкой не переносятся.
Полная начальная индексация mainnet с пользовательским GetBlock в облаке не
выполнялась; тесты используют настоящий PostgreSQL 17 и локальные RPC fixtures.

## Проверки

```sh
source /workspace/.tools/stakedao/env.sh
go test -mod=readonly -race -p 3 ./internal/service/prices ./internal/service/stakedao ./internal
```

Тесты используют локальные HTTP/RPC-стенды и подготовленные данные, без запросов
к бесплатной ноде или внешнему источнику цен. Покрываются расчёт TVL, отсутствие цен/decimals,
изоляция сетей, одновременные обращения к кэшу, определение Accountant и ошибки
его чтения. Тесты проверяют формулы наград, обе политики комиссий, Sidecar, срок наград,
масштабирование rates, неполные данные и отсутствие лишних удержаний комиссий.
Они не подтверждают актуальные live-значения пулов mainnet.
