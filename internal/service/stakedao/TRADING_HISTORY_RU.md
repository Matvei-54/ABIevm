# Историческая торговая APY: окна 7 и 30 дней

Для проверенных fixed-rate Curve-пулов реализована onchain-оценка дохода LP
от комиссий по изменению `get_virtual_price()` между двумя блоками.
Используются два независимых окна: **7 дней** и **30 дней**. Основной `apy`
и `yieldBreakdown.trading.apy` относятся к 30-дневному окну;
`apyScope: "trading_fees"`. Верхний `apr` по-прежнему относится к vault_rewards.
Эти показатели автоматически не складываются в общий APR/APY.

Это измерение retained fee growth LP в единицах инварианта для ограниченной
проверенной модели. Оно включает удержанные LP комиссии обменов и операций
ликвидности, не является отчётом USD-объёма всех сделок и не учитывает изменение
рыночной USD-цены/impermanent loss. История всех swap-транзакций не скачивается.
Годовой показатель экстраполирует наблюдавшийся период, не обещает будущий доход.

## Почему сразу два окна

- 7 дней быстрее отражают изменение торговой активности; одна необычная неделя
  сильнее влияет на годовой показатель.
- 30 дней сглаживают кратковременные изменения, но медленнее реагируют на новый
  режим торговли. Это rolling 30 суток, не календарный месяц.

Неделя не считается «точно достаточной». В ответе видны оба результата,
реальные границы и статус каждого окна. Если доступны только 7 дней,
основной 30-дневный `apy` остаётся null: скрытой замены периода нет.
`trading.status` может быть partial, если рассчитано лишь одно из окон.

## Поддержанные маршруты

| LP / pool | Модель |
| --- | --- |
| crvUSD/USDC `0x4dece678ceceb27446b35c672dc7d61f30bad69e` | Plain pool, фиксированные rate multipliers, USDC/crvUSD |
| crvUSD/USDT `0x390f3595bca2df7d23783dfd126427cceb997bf4` | Plain pool, фиксированные rate multipliers, USDT/crvUSD |
| frxETH/WETH `0x9c3b46c0ceb5b9e304fcd6d88fc50f7dd24b31bc` | Plain EMA pool, WETH и non-rebasing frxETH, фиксированные rate multipliers |
| BOLD/USDC `0xefc6516323fbd28e80b85a497b65a86243a54b3e` | StableSwap NG, только standard asset types и фиксированная нормализация |

У обоих концов окна проверяются точные адреса и порядок coins. У NG дополнительно
читается factory `get_pool_asset_types(pool)`: оба типа должны быть Standard=0;
`stored_rates()` должны равняться 1e18 / 1e30 для BOLD / USDC.
Только совпадения stored_rates на двух блоках недостаточно для доказательства
отсутствия oracle/rebasing/ERC4626-доходности; поэтому нужен asset-type guard.

Прочие LP, включая weETH/WETH с динамическим rate, ERC4626-компоненты,
metapools и crypto-пулы, не оцениваются этой формулой автоматически:
`unsupported_pool_model`, APY=null. Их поддержка требует отдельной модели.
Не всякий рост virtual price можно корректно назвать торговыми комиссиями.

## Контракты и формула

На каждом конце окна читаются:

```text
pool.get_virtual_price()
pool.initial_A(), pool.future_A()
pool.initial_A_time(), pool.future_A_time()
pool.coins(0), pool.coins(1)
```

Для NG также:

```text
factory 0x6A8cbed756804B16E05E741eDaBd5cB544AE21bf.get_pool_asset_types(pool)
pool.stored_rates()
```

Исключаются периоды, затронутые ramp A, включая завершённое изменение внутри
окна. Сравниваются параметры и timestamps обоих snapshots; одинаковые конечные
значения virtual price сами по себе не доказывают неизменность A.
Изменения A, закончившиеся до начала окна, не мешают расчёту.

```text
growth = VP_end / VP_start - 1
observedReturnPercent = growth × 100
APY = ((1 + growth)^(31536000 / actualElapsedSeconds) - 1) × 100
```

Для вычислений используются точное decimal-отношение и log1p/expm1, чтобы
сохранить точность малых доходностей. Нулевой проверенный рост даёт APY=0.
Уменьшение virtual price, неправильные параметры, чрезмерный/нечисловой
результат оставляют показатель недоступным; отрицание проблемы нулём не делается.

Блок начала ищется по timestamp, а не вычисляется только через «7200 блоков/сутки».
12 секунд используются лишь для начальной границы бинарного поиска.
Выбирается последний блок не позднее target; разрыв границы свыше 120 секунд
не допускается. Сохранены фактические timestamps и coveredSeconds между ними;
это длина окна, не утверждение о прочитанности всех полей при unavailable.
Оба hash фиксируются, старый блок проверяется повторно, конечный hash проверяется
существующей проверкой всего ответа.

## Что изменилось в JSON

В подробном ответе:

- `apyScope="trading_fees"`;
- `yieldBreakdown.trading.source="curve_onchain_fee_growth"`;
- `scope="fixed_rate_lp_fee_growth"`, адрес pool и основной windowDays=30;
- `windows`: отдельные записи 7/30 с APY, наблюдавшимся return, статусом,
  причинами, номерами/временем/hash блоков и raw virtual prices как строки.

Краткий ответ сохраняет шесть полей; `status` по-прежнему описывает APR.
Доступность APY и выбранный период смотрятся в подробном trading-компоненте.
Новая APY не является реинвестированным вариантом CRV APR.

Проверка:

```text
GET /reservesStakedao/ethereum/diagnostics?gauges=0x07a01471fA544D9C6531B631E6A96A79a9AD05E9&strictPrices=true
```

При параметре block периоды отсчитываются от времени **этого** блока.
Обычный основной endpoint также получает APY для поддержанных пулов.
Endpoint `/state` не вызывает эту историю и остаётся лёгким.

## Требования к RPC и обработка отказов

Нужен доступ к **eth_call на состояниях 7/30 дней назад**. Возможность получить
старый Header/номер блока этого не гарантирует. URL по-прежнему задаётся через
STAKEDAO_ETHEREUM_RPC_URL; отдельного RPC/fallback или API StakeDAO не добавлено.

При явном отказе провайдера в архивном доступе возвращается `archive_rpc_required`.
Другие отсутствующие/несовместимые исторические состояния отмечаются отдельно
как `historical_state_unavailable_or_incompatible`. Ошибка истории сохраняется
в trading-компоненте и не делает уже рассчитанный CRV APR недоступным.
Общая отмена/таймаут запроса и общий RPC budget по-прежнему завершают запрос.
RPC URL/ключи не включаются в причины.

Границы окон переиспользуются между пулами одного запроса. У сервиса есть
ограниченный кэш до 256 успешных snapshots по pool+blockHash, без БД и миграций.
Ошибки и отказы архива в нём не сохраняются. Не выполняется полная индексация
логов, поэтому проверенный диапазон eth_getLogs=1500 здесь не используется.
Исторические чтения учитываются действующим RPS и sample budget.

## Валидация и её пределы

Тесты с детерминированными контрактными snapshots проверили численные APY 7/30,
точные временные границы, нулевой рост, fixed-rate NG guard, изменение A,
положительное недельное окно при недоступном месячном без подстановки,
ошибочный coin mapping, уменьшение virtual price, отказ архива, reorg старого
блока, кэширование и независимость CRV. Все обычные тесты остаются без mainnet.

На mainnet через PublicNode подтверждены текущие getters и NG asset-type/rates.
Реальный bounded diagnostic BOLD/USDC на блоке **26449644** завершился за
**16.058 секунды, 80 RPC**, без ошибок полей текущего APR. CRV APR available,
исторические окна 7 и 30 unavailable с `archive_rpc_required`: PublicNode
потребовал персональный токен для старого состояния. Это не результат нулевой APY.
Сохранён [JSON этого отказа](../../../examples/stakedao-trading-archive-required.json).
**Положительные mainnet APY 7/30 через этот RPC не получены**; нужны разрешённые
архивные чтения для такой проверки. GetBlock CU не использовались.

Позднее пользователь предоставил успешный ответ Alchemy на блоке 26450201.
Четыре исторические APY независимо пересчитаны из raw virtual prices; совпадение
арифметики и данные записаны в
[BOLD_ROUTE_AND_WEETH_MODEL_RU.md](BOLD_ROUTE_AND_WEETH_MODEL_RU.md).

## Про shutdown и Merkl

Shutdown читается из смартконтракта ProtocolController StakeDAO. Это отключение
регистрации/стратегии StakeDAO для gauge, не утверждение, что Curve AMM перестал
торговать. Основной список уже исключает shutdown до поиска цен и истории;
предварительно вызывать `/state` вручную не требуется. Этот endpoint полезен
для проверки отключённой/неизвестной регистрации без загрузки доходности.

Реестр Merkl пока не реализован. Его базу можно построить через RPC по
nbIncentives/incentives(id) и событиям, с локальным курсором и кэшем. API StakeDAO
для этого не обязателен. При этом eligibility/proof и некоторые типы кампаний
могут требовать внешних данных; один onchain Merkle root не раскрывает весь
расчёт распределения. Это отдельная задача и не часть добавленной fee APY.

Источники модели: верифицированные контракты четырёх перечисленных пулов;
[Plain2BasicEMA](https://github.com/curvefi/curve-factory/blob/5272fd2b1199f185d9cd94822be9262c387dc2c2/contracts/implementations/plain-2/Plain2BasicEMA.vy),
[официальный Curve API getVolumes](https://github.com/curvefi/curve-api/blob/799af539234602bea4f0caa770cce2176ca9f7cd/routes/v1/getVolumes/%5BblockchainId%5D.js).
Последний показал, что base APY может включать LST yield; его готовое значение
не импортируется в runtime как торговая APY. Точное совпадение с UI StakeDAO,
использующим свой период/аналитику, этим исследованием не объявляется.
